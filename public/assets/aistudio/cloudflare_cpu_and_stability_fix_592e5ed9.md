# دفعة المهام الحرجة (Root-Cause Fix for Cloudflare Worker CPU Time Limit & Build Stability)

<project_context>
- **المشروع:** تطبيق ويب (`3fetyayouth.online`) مرتبط بـ Worker باسم (`threefetyayouth-api`).
- **المشكلة الكارثية الحالية (Runtime CPU Limit):**
  أرسل Cloudflare تحذيراً بأن الـ Worker تجاوز الحد الأقصى لوقت المعالجة في الخطة المجانية (`Free tier CPU time limit: 10ms per invocation`) أكثر من 100+ مرة خلال 24 ساعة، مما يؤدي لإيقاف الـ Worker في منتصف المهمة وفشل طلبات الـ API.
- **مشكلة البناء (Build/Cache Issue):**
  تعارض في ملفات `bunfig.toml` / `bun.lock` المخزنة في الكاش أثناء الـ Deployment.
- **الهدف النهائي:** إعادة هيكلة كود الـ Worker والـ Client Sync لضمان ألا يتجاوز استهلاك الـ CPU في أي طلب 1ms إلى 3ms كحد أقصى للأبد، وحل مشكلة البناء نهائياً.
</project_context>

<tasks>
نفذ المهام الـ 5 التالية بدقة صارمة وجذرية، وافصل بين حل كل مهمة بعنوان واضح (`## Task 1`, `## Task 2`...):

### Task 1: علاج السبب الرئيسي لاستنزاف الـ CPU في الـ Worker (إلغاء معالجة الـ JSON الضخم والـ Base64 في كل طلب)
- **التشخيص التقني:** في الخطة المجانية لـ Cloudflare Workers، الحد الأقصى للـ CPU هو `10ms` فقط لكل Request. قيام الـ Worker بقراءة وفك تشفير (`JSON.parse`) وإعادة تشفير (`JSON.stringify`) لكائن حالة كامل (Full State Object) يحتوي على جميع الأعضاء + الصور الشخصية (Base64) + صور الإعلانات (Base64) + الحضور في كل طلب يستهلك أكثر من 20-50ms فيقتل الـ Worker فوراً!
- **المطلوب تنفيذه في كود الـ Worker والـ Backend:**
  1. **منع الـ `JSON.parse` غير الضروري (Raw Streaming / Pass-through):** عند طلب قراءة البيانات (`GET`) من Cloudflare KV / D1 / Durable Objects، لا تقم بعمل `JSON.parse` ثم `JSON.stringify` داخل الـ Worker إذا لم تكن هناك حاجة لتعديل البيانات في الـ Worker؛ أرسل النص المخزن مباشرة كـ `new Response(rawString, { headers: { 'Content-Type': 'application/json' } })` لتوفير 90% من وقت الـ CPU.
  2. **فصل الصور الثقيلة (Base64 Images) عن بيانات المزامنة الدورية:** افصل الصور الشخصية (`avatar`) وصور الإعلانات الكبيرة في مفاتيح/جداول مستقلة (أو لا تقم بإرسالها في كل طلب Polling دوري كل بضع ثوانٍ)، واجعل المزامنة اللحظية تنقل فقط البيانات النصية الخفيفة والتغييرات (`Delta Updates`).
  3. **إلغاء التشفير الثقيل داخل الـ Worker:** إذا كان هناك تشفير كلمات مرور ثقيل (مثل `bcrypt` بعدد جولات عالٍ) يعمل داخل الـ Worker، استبدله بـ `Web Crypto API` الأصلي السريع جداً (`crypto.subtle.digest('SHA-256', ...)`) لأنه يعمل بـ C++ Native ولا يستهلك وقت CPU من حصة الـ Worker.

### Task 2: إضافة طبقة تخزين مؤقت لحظية على حافة الشبكة (Cloudflare Edge Cache / ETag)
- **المطلوب بالتفصيل:**
  1. أضف آلية `ETag` أو `lastUpdatedVersion` (رقم إصدار أو Timestamp خفيف جداً).
  2. عندما يسأل المتصفح (Polling) عن التحديثات، يرسل معه `lastVersion`؛ يتحقق الـ Worker من الرقم فقط، وإذا لم يتغير شيء، يرجع فوراً `304 Not Modified` (أو `{ changed: false }`) في أقل من `0.2ms` من وقت الـ CPU بدون قراءة أو إرسال قاعدة البيانات بالكامل!
  3. عند حدوث تعديل جديد (`POST` / `PUT`)، يتم تحديث رقم الـ `version` لمزامنة جميع الأجهزة فوراً.

---

### Task 3: ترشيد استعلامات الواجهة الأمامية (Smart Client-Side Polling & Debouncing)
- **المطلوب بالتفصيل في كود الواجهة الأمامية (`cloudSync` / `App.tsx`):**
  1. **إيقاف المزامنة في الخلفية (Visibility API):** إذا كانت علامة تبويب المتصفح أو التطبيق في الخلفية (`document.hidden === true`)، أوقف الـ Polling الدوري فوراً، واستأنفه بمجرد فتح المستخدم للشاشة (`visibilitychange`).
  2. **منع الطلبات المتداخلة (Request Deduplication & Debounce):** امنع إرسال أكثر من طلب مزامنة في نفس اللحظة، واجعل تعديلات الأدمن (مثل تعديل النصوص أو الحضور) تُرسل عبر `Debounce` ذكي لمنع إغراق الـ Worker بمئات الطلبات في الثانية.
